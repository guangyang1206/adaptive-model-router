## English

### Adaptive Model Router 0.1.0 — task-aware model routing that lives inside the agent loop

Agent apps rarely want one model. A planning step wants reasoning. A tool-call
step wants reliable JSON. An extraction step wants something cheap. A final
answer wants quality. Most codebases resolve this the same way: hard-code one
model and accept it is either too expensive for the easy steps or too weak for
the hard ones. The second stage is a growing thicket of `if step == "plan"`
branches, a retry wrapper someone added during an outage, and no record of why
any given request went where it went.

Gateways solve a real and adjacent problem — one API across many providers, keys
in one place, spend in one dashboard. But a gateway sits in front of your app,
not inside it. By the time a request arrives, the agent's own context is gone:
which step this is, what the step is allowed to cost, whether a previous attempt
already failed. The gateway sees an HTTP body.

Adaptive Model Router is an SDK you embed in the agent runtime instead. It picks
a model from task context and capability constraints, records every fallback
attempt, and explains each decision in a local dashboard.

Four packages are now on npm at `0.1.0`, Apache-2.0, Node 20+:
`@adaptive-router/sdk`, `/dashboard`, `/cli`, `/control-plane`.

### What it actually does

**Routing is a decision you can read back.** Candidates are scored on
capability, model tier, health and success signal, latency, then cost. The
returned `routerTrace` carries the chosen model, the reason, and the full
candidate list — including, for every model that lost, all the reasons it was
skipped, in priority order. A model can be both disabled and missing a
capability; both are recorded, because collapsing that into one reason is how
routing becomes unexplainable.

**Seven providers, one shape.** OpenAI, Anthropic, Gemini, DeepSeek, Qwen,
Ollama, and self-hosted vLLM. Provider quirks stay inside the adapter.

**The SDK has no runtime dependencies.** Not "few" — `dependencies: {}`,
enforced in CI by a dependency-boundary check that fails the build. Installing
it reports `added 1 package`. Postgres and OAuth exist only in the optional
control-plane package.

**Framework adapters with no framework dependency.** `createLangChainModel()`
and `createVercelModel()` work without `@langchain/core` or the Vercel AI SDK
installed, and the `routerTrace` survives the framework hop.

**Degradation is loud, not silent.** The semantic cache falls back to
exact-match when no real embedding provider is wired, and says so. Learned
routing weights are never auto-adopted — a human calls `adoptWeights`
explicitly. The eval harness never issues real network calls.

**Optional self-hosted team plane.** Organizations and projects, Better-Auth,
Postgres, docker-compose and a Render blueprint. Project isolation is
structural: the data source captures `projectId` at construction, so every query
is forced through `WHERE project_id = $1`.

### Try it in about two minutes

This makes a routing decision without calling any provider, so it needs no API
key and no network:

```bash
npm install @adaptive-router/sdk

node --input-type=module -e "
import { createRouter, createStaticProvider } from '@adaptive-router/sdk'
const models = [{ id: 'local/demo', provider: 'demo', model: 'demo', type: 'self-hosted',
  kind: 'openai-compatible', tier: 'balanced', contextWindow: 8192,
  capabilities: ['reasoning'], enabled: true,
  cost: { inputPer1M: 0, outputPer1M: 0, currency: 'USD', estimated: true },
  health: { status: 'ok', successRate: 1 } }]
const router = createRouter({ providers: [createStaticProvider('demo', models)], models })
const e = await router.evaluate({ messages: [{ role: 'user', content: 'Plan a task.' }], route: { task: 'plan' } })
console.log('ranked candidates:', e.candidates.length)
"
```

`evaluate()` only ranks; `chat()` is what actually calls a provider. Full path
with real providers and the dashboard: [Quickstart](../en/quickstart.md).

### What it does not do

This is a `0.1.0`. Being precise about the edges matters more than the pitch:

- **No performance or cost claims.** No comparative benchmarks have been run, so
  there are no numbers here. Routing decisions are explainable; whether they are
  *better* than your hand-written logic is unproven and depends on your models.
- **No real-time answer quality judgment.** Routing uses capability metadata,
  health, latency, and cost — not an assessment of whether an answer was good.
- **No mid-stream fallback.** Fallback, retry, and timeout cover non-streaming
  calls. Once a stream has started, a failure is not recovered; the trace notes
  that fallback was disabled.
- **Control-plane RBAC is partial.** Only `owner` and `member` are enforced.
  `admin` and `viewer` are reserved and render disabled.
- **No audit log, no team budgets, no organization-level provider keys.** All
  deferred, all listed as deferred in the roadmap.
- **The SQLite store is not at parity with JSONL.** It omits the cache-lookup
  and weights-change event streams. Documented, and an open issue.
- **Releases are still published by hand.** Automated publishing with provenance
  is the next distribution task.

### What would help most

Not stars. What the roadmap is missing is knowledge of how this behaves in a
codebase that is not mine. The next milestone's scope is deliberately unlocked
until there is real usage to point at.

Most useful, roughly in order:

1. **Tell us what you are routing between, and what decided it.** Not a bug
   report — just your actual setup. Two local models and one cloud model? Cost
   ceiling per step? Which step made you reach for a router at all?
2. **Tell us where the routing decision was wrong.** A `routerTrace` where the
   chosen model is not what you would have picked is the single highest-value
   thing you can send. It is a self-contained, reproducible artifact.
3. **Tell us what broke in the first ten minutes.** Install, types, a provider
   that would not authenticate. Early friction is invisible to whoever wrote it.

## 中文版

### Adaptive Model Router 0.1.0 — 跑在 agent 循环内部的任务感知模型路由

Agent 应用很少只需要一个模型。规划步骤要推理能力，工具调用步骤要稳定的 JSON，
抽取步骤要便宜，最终回答要质量。大多数代码库的处理方式是一样的：写死一个模型，
然后接受它对简单步骤太贵、对困难步骤又不够用。接下来就是越来越密的
`if step == "plan"` 分支、某次故障时临时加上的重试包装，以及完全没有记录——
没人说得清某个请求当初为什么走了那条路。

网关解决的是一个真实且相邻的问题：一套 API 对接多家供应商、密钥集中管理、
花费集中查看。但网关站在你的应用**前面**，而不是里面。请求到达网关时，
agent 自己的上下文已经丢了：这是哪一步、这一步允许花多少、之前是不是已经失败过一次。
网关看到的只是一个 HTTP body。

Adaptive Model Router 换了个位置：它是一个嵌进 agent 运行时的 SDK。
它按任务上下文和能力约束选模型，记录每一次 fallback 尝试，
并在本地看板里解释每一次决策。

四个包现已发布到 npm，版本 `0.1.0`，Apache-2.0，Node 20+：
`@adaptive-router/sdk`、`/dashboard`、`/cli`、`/control-plane`。

### 它具体做什么

**路由决策是可以回读的。** 候选模型按能力、档位、健康与成功率信号、延迟、
最后成本依次打分。返回的 `routerTrace` 带着选中的模型、原因，以及完整候选列表——
对每个落选模型，都记录它被跳过的**全部**原因，按优先级排列。一个模型可能既被禁用、
又缺少某项能力；两条都会记下来，因为把它们压成一条，正是路由变得无法解释的起点。

**七个 provider，一套形状。** OpenAI、Anthropic、Gemini、DeepSeek、Qwen、
Ollama，以及自托管 vLLM。供应商的怪癖全部关在适配器内部。

**SDK 没有运行时依赖。** 不是"很少"，而是 `dependencies: {}`，
由 CI 里的依赖边界检查强制执行，越界直接构建失败。安装时输出
`added 1 package`。Postgres 和 OAuth 只存在于可选的 control-plane 包里。

**框架适配器不依赖框架。** `createLangChainModel()` 和 `createVercelModel()`
在没有安装 `@langchain/core` 或 Vercel AI SDK 的情况下也能工作，
并且 `routerTrace` 能穿过框架这一跳保留下来。

**降级是出声的，不是静默的。** 语义缓存在没有接入真实 embedding provider 时
退回精确匹配，并且明确告知。学到的路由权重永不自动采用——必须由人显式调用
`adoptWeights`。评测工具链从不发出真实网络请求。

**可选的自托管团队控制面。** 组织与项目两级、Better-Auth、Postgres、
docker-compose 和 Render 蓝图。项目隔离是结构性的：数据源在构造时就固定
`projectId`，因此每条查询都被强制带上 `WHERE project_id = $1`。

### 它做不到什么

这是一个 `0.1.0`。把边界说准，比把话说漂亮更重要：

- **不给性能或成本结论。** 项目没有跑过对比测试，所以这里没有任何数字。
  路由决策是可解释的；但它是否比你手写的逻辑**更好**，未经验证，
  且取决于你用的是哪些模型。
- **没有实时答案质量判定。** 路由依据是能力元数据、健康度、延迟和成本，
  不是对"这个回答好不好"的评估。
- **没有流式中途 fallback。** fallback、重试、超时覆盖的是非流式调用。
  流一旦开始，失败不会被接管；trace 里会记下 fallback 已被禁用。
- **控制面的 RBAC 不完整。** 只有 `owner` 和 `member` 生效，
  `admin` 与 `viewer` 是预留的，界面上渲染为禁用态。
- **没有审计日志、没有团队预算、没有组织级 provider 密钥。**
  全部延后，且在路线图里明确标为延后。
- **SQLite 存储与 JSONL 不对等。** 它缺少 cache-lookup 和 weights-change
  两条事件流。这一点已写进文档，并且有对应的待办 issue。
- **发布目前仍是手工执行的。** 带 provenance 的自动发布是下一个分发任务。

### 最需要什么帮助

不是 star。路线图现在缺的是"它在别人代码库里表现如何"这类认知。
下一个里程碑的范围被刻意留空，直到有真实使用情况可以指着说事。

最有用的，大致按顺序：

1. **告诉我们你在哪些模型之间做路由，以及是什么决定了选择。**
   不用是 bug 报告，就说你实际的配置。两个本地模型加一个云端模型？
   每步有成本上限？到底是哪一步让你需要一个路由器？
2. **告诉我们路由决策在哪里判断错了。** 一份"选中模型不是你会选的那个"的
   `routerTrace`，是你能提供的最高价值的东西——它自带上下文，且可复现。
3. **告诉我们前十分钟里什么卡住了。** 安装、类型、某个 provider 死活认证不过。
   早期摩擦对写这份代码的人来说是看不见的。
